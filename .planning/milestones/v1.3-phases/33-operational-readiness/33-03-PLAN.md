**Specific runbook content:**

**dns-down.md:** DNS resolution failure
- Quick actions: check dnsdist pods, check unbound pods, check policy-svc pods, test resolution with drill/dig, check upstream connectivity
- Common causes: dnsdist crash (30%), Unbound cache corruption (20%), upstream resolver failure (20%), LoadBalancer IP change (15%), policy-svc unavailable (15%)
- Cross-references: redis-down.md, policy-svc-crash.md
- Key commands: `kubectl get pods -n nebula-dns`, `kubectl logs -n nebula-dns deploy/dnsdist`, `drill @<loadbalancer-ip> google.com`, `kubectl exec -n nebula-dns deploy/dnsdist -- echo "showServers()" | nc 127.0.0.1 5199`

**database-down.md:** PostgreSQL/ClickHouse failure
- Quick actions: check PostgreSQL via DigitalOcean dashboard, test connectivity with psql, check API pod logs for connection errors, check ClickHouse Cloud status
- Common causes: DigitalOcean managed DB maintenance (40%), connection pool exhaustion (30%), credential rotation (15%), network partition (15%)
- Key commands: `kubectl logs -n nebula-dns deploy/api --tail=50 | grep -i "database\|postgres\|connection"`, check PgBouncer stats
- ClickHouse section: check Cloud dashboard, verify query_logs ingestion, curl health endpoint

**redis-down.md:** Redis/Valkey cache failure
- Quick actions: check DigitalOcean Valkey dashboard, test connectivity, check policy-svc logs, verify TLS certificates
- Common causes: managed Valkey maintenance (35%), TLS certificate expiry (25%), memory limit hit (20%), credential rotation (20%)
- Impact: policy cache invalidation stops, stale policies served, new policy changes not propagated
- Key commands: `kubectl exec -n nebula-dns deploy/policy-svc -- redis-cli -u $REDIS_URL ping`, check Valkey metrics in DO dashboard

**policy-svc-crash.md:** Policy service crash loop
- Quick actions: check pod status, view recent logs, check Redis connectivity, verify ClickHouse connection, check OOM kills
- Common causes: Redis connection failure (60%), OOM killed (25%), ClickHouse unavailable (10%), image pull error (5%)
- How startup works: connects to Redis → loads policy cache → connects to ClickHouse → starts HTTP server → readiness probe passes
- Warning signs: `policy_cache_load_duration_seconds` > 30s, `redis_connection_errors_total` spikes, `go_memstats_alloc_bytes` approaching limit
- Key commands: `kubectl describe pod -n nebula-dns -l app=policy-svc`, `kubectl logs -n nebula-dns -l app=policy-svc --previous`

**cert-expiration.md:** TLS certificate issues
- Quick actions: check cert-manager certificate status, check certificate events, check ACME challenge status, verify DNS-01 solver
- Common causes: cert-manager pod down (30%), DNS-01 challenge failure (30%), Let's Encrypt rate limit (20%), DNS propagation delay (20%)
- Key commands: `kubectl get certificates -n nebula-dns`, `kubectl describe certificate -n nebula-dns`, `kubectl logs -n cert-manager deploy/cert-manager`
- Emergency: manual cert renewal with certbot if cert-manager unrecoverable

Per user decision: Hybrid format with quick-action checklist first, detailed explanation below. No escalation tiers.

**Deployment Runbook (docs/runbooks/deployment.md):**

Create a production deployment procedure document covering:

1. **Pre-Deployment Checklist:**
   - [ ] CI/CD pipeline passed (all tests green)
   - [ ] Docker images pushed to DOCR
   - [ ] Staging deployment verified
   - [ ] Database migrations tested (if any)
   - [ ] Changelog reviewed
   - [ ] Monitoring dashboards open

2. **Deployment Procedure:**
   - Standard: Use GitHub Actions deploy.yml with manual production approval
   - Manual fallback: `helm upgrade nebula-dns ./helm/safedns -n nebula-dns -f helm/safedns/values-production.yaml --atomic --timeout 15m --history-max 10`
   - Post-deployment verification:
     - `kubectl rollout status deployment/api -n nebula-dns --timeout=300s`
     - `kubectl rollout status deployment/policy-svc -n nebula-dns --timeout=300s`
     - `kubectl rollout status statefulset/unbound -n nebula-dns --timeout=300s`
     - Health check endpoints: curl API /healthz, test DNS resolution
     - Check Grafana SLO dashboard for degradation

3. **Deployment Strategies:**
   - Current: Rolling update (maxSurge: 1, maxUnavailable: 0)
   - Why: Cost-efficient, no 2x infrastructure. Brief DNS latency spike during cache warm-up (~30s) acceptable.
   - Future consideration: Blue-green via Argo Rollouts if SLO violations occur during deployments

4. **Post-Deployment Monitoring:**
   - Watch for 15 minutes post-deploy
   - Check error rates in Prometheus/Grafana
   - Verify DNS query success rate stays >99.9%
   - Check pod restart counts

**Rollback Runbook (docs/runbooks/rollback.md):**

Create a deployment rollback procedure:

1. **When to Rollback:**
   - Error rate exceeds 1% after deployment
   - p95 latency >200ms sustained for 5+ minutes
   - Health check endpoints returning 503
   - CrashLoopBackOff on new pods

2. **Quick Rollback (DO THIS FIRST):**
   - [ ] `helm rollback nebula-dns -n nebula-dns`
   - [ ] Verify: `kubectl rollout status deployment/api -n nebula-dns`
   - [ ] Verify: `kubectl rollout status deployment/policy-svc -n nebula-dns`
   - [ ] Check health endpoints return 200
   - [ ] Verify DNS resolution works

3. **Rollback to Specific Version:**
   - List history: `helm history nebula-dns -n nebula-dns`
   - Rollback to revision: `helm rollback nebula-dns <REVISION> -n nebula-dns`
   - Note: `--history-max 10` limits available rollback revisions

4. **Database Migration Rollback:**
   - If migration was part of deployment: `./scripts/rollback-migration.sh`
   - Warning: Data migrations may not be reversible
   - Check migration status: `kubectl logs -n nebula-dns job/db-migration`

5. **Post-Rollback:**
   - Verify all services healthy
   - Document what went wrong
   - Create follow-up issue for root cause analysis
   - Consider: Was the issue caught by staging? If not, why?

Per user decision: Hybrid format. Rolling update strategy (not blue-green/canary per research recommendation). Cross-reference between deployment and rollback runbooks.
