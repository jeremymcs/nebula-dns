<objective>
Make ClickHouse schema environment-aware (MergeTree for Cloud, ReplicatedMergeTree for self-hosted) and incorporate the full production schema including retention tables, materialized views, and threat/audit logs.

Purpose: ClickHouse Cloud manages replication automatically and requires plain MergeTree engines. Self-hosted ClickHouse needs ReplicatedMergeTree for multi-replica setups. The Helm template must conditionally select the correct engine based on the `clickhouse.cloud` value. Additionally, the production schema must include all tables defined in `init-clickhouse-retention.sql` (threat_logs, audit_logs, performance_metrics, materialized views) that are currently missing from the Helm init job.

Output: Environment-aware Helm template, updated standalone Kustomize job, updated local dev script.
</objective>

    **Update `helm/safedns/templates/clickhouse-init-job.yaml`:**

    1. **HTTPS support for ClickHouse Cloud**: The init container and main container currently use HTTP (`http://{{ .Values.clickhouse.host }}:{{ .Values.clickhouse.port }}`). ClickHouse Cloud requires HTTPS on port 8443. Add conditional protocol selection:
       ```yaml
       {{- $ch_protocol := ternary "https" "http" .Values.clickhouse.cloud }}
       {{- $ch_port := ternary (.Values.clickhouse.cloudPort | default 8443) (.Values.clickhouse.port | default 8123) .Values.clickhouse.cloud }}
       ```
       Use these variables in both the init container curl and the main container curl commands. For HTTPS, add `--insecure` flag OR better, use the `--cacert` approach. For simplicity and because ClickHouse Cloud uses valid TLS certs, just switch to `https://` with no extra flags needed.

    2. **Environment-aware engine selection in the embedded SQL ConfigMap**: Use Helm templating to conditionally set engine types:
       - For `query_logs` table:
         ```sql
         {{- if .Values.clickhouse.cloud }}
         ENGINE = MergeTree()
         {{- else }}
         ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/query_logs', '{replica}')
         {{- end }}
         ```
       - For `hourly_stats`, `category_stats`, `domain_stats` tables:
         ```sql
         {{- if .Values.clickhouse.cloud }}
         ENGINE = SummingMergeTree()
         {{- else }}
         ENGINE = ReplicatedSummingMergeTree('/clickhouse/tables/{shard}/TABLE_NAME', '{replica}')
         {{- end }}
         ```

    3. **Canonical partitioning scheme** (IMPORTANT — resolves inconsistency between init-clickhouse.sql and init-clickhouse-retention.sql):
       - `query_logs`: Use `PARTITION BY toYYYYMMDD(timestamp)` — this matches the existing init-clickhouse.sql (line 29) and the phase success criteria. Daily partitions are correct for query_logs because it is the highest-volume table and daily granularity enables efficient partition-level TTL drops. Do NOT use the retention script's `toYYYYMM(event_date)` scheme for this table.
       - `threat_logs`: Use `PARTITION BY toYYYYMM(event_date)` — monthly partitions are appropriate because threat logs are much lower volume than query_logs and have a 180-day TTL. Monthly partitions keep the partition count manageable.
       - `audit_logs`: Use `PARTITION BY toYYYYMM(event_date)` — monthly partitions are appropriate because audit logs have a 7-year retention and daily partitions would create excessive partition count (2500+ partitions).
       - `performance_metrics`: Use `PARTITION BY toYYYYMM(event_date)` — monthly partitions are appropriate for this low-volume metrics table with 30-day TTL.
       - `hourly_stats`, `category_stats`, `domain_stats`: Keep existing `toYYYYMM` partitioning (already in init-clickhouse.sql). These are aggregation tables with lower volume.
       - Materialized views (`query_logs_hourly`, `query_logs_daily`): Use `toYYYYMM` partitioning (matching retention script).

    4. **Add missing production tables from init-clickhouse-retention.sql**. Incorporate these tables into the ConfigMap SQL (with environment-aware engine selection and partitioning scheme from step 3):
       - `threat_logs` table (MergeTree, `toYYYYMM(event_date)`, 180-day TTL)
       - `audit_logs` table (MergeTree, `toYYYYMM(event_date)`, 7-year TTL for compliance)
       - `performance_metrics` table (MergeTree, `toYYYYMM(event_date)`, 30-day TTL)

       For each, use the same conditional engine pattern. Use the column definitions from `scripts/init-clickhouse-retention.sql` exactly. Include `event_date Date DEFAULT toDate(timestamp)` column and `ttl_only_drop_parts = 1` setting.

    5. **Add materialized views** from the retention script:
       - `query_logs_hourly` materialized view (hourly aggregation, 1-year TTL)
       - `query_logs_daily` materialized view (daily aggregation, 2-year TTL)

       Note: Materialized views use the same SummingMergeTree engine conditional.

    6. **Add helper views** (these are simple VIEWs, no engine conditional needed):
       - `v_top_blocked_domains`
       - `v_hourly_summary`
       - `v_active_threats`

    7. **Expand verification** in the main container script to check for ALL tables, not just `query_logs`:
       ```bash
       for table in query_logs hourly_stats category_stats domain_stats threat_logs audit_logs performance_metrics; do
         if echo "$TABLES" | grep -q "$table"; then
           echo "OK: $table exists"
         else
           echo "FAIL: $table missing"
           exit 1
         fi
       done
       ```

    8. **Do NOT include sample data INSERTs** from the dev script. Production schema should be clean.

    9. **Do NOT include SYSTEM STOP/START MERGES** commands from retention script. Those are operational tuning, not schema initialization.

    10. Ensure the copyright header is present.
  </action>
