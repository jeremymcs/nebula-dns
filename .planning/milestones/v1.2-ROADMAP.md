## Overview

This milestone delivered role-based access control, admin user management, and alerting integrations for Mission Control. RBAC was foundational and completed first, followed by admin management and alerting which proceeded in parallel. Migration & rollout was the final phase to safely enable enforcement.

**Core Value:** Enable ops team to manage MSPs entirely through the UI — with proper role separation and proactive alerting.

## Phases

### Phase 17: RBAC Foundation (Backend)

**Goal:** Backend infrastructure for role-based access control is complete and ready for enforcement.
**Depends on:** None (first phase of v1.2)
**Plans:** 4 plans

Plans:
- [x] 17-01-role-infrastructure-PLAN.md — Create AdminRole enum, decorator, guard, and migration
- [x] 17-02-jwt-auth-integration-PLAN.md — Integrate role into JWT and auth flow
- [x] 17-03-endpoint-annotation-PLAN.md — Apply role requirements to all endpoints
- [x] 17-04-self-escalation-breakglass-PLAN.md — Add protections and break-glass script

**Requirements:**
- RBAC-01: Admin entity has role column (super_admin, admin, viewer)
- RBAC-02: AdminRolesGuard validates role against required roles per endpoint
- RBAC-03: @AdminRoles() decorator specifies required roles on controllers
- RBAC-04: Admin JWT contains role claim for frontend permission checks
- RBAC-05: All /admin/* endpoints have role requirements defined
- RBAC-08: Viewer role has read-only access (403 on mutating actions)
- RBAC-09: Server rejects self-role-escalation attempts with 403
- RBAC-10: Break-glass Super Admin account exists before enforcement

**Success Criteria:**
1. ✓ Admin can authenticate and receive JWT containing role claim
2. ✓ GET requests to /admin/* succeed for all roles (super_admin, admin, viewer)
3. ✓ POST/PUT/DELETE requests return 403 for viewer role
4. ✓ Attempt to change own role to higher level returns 403
5. ✓ At least one super_admin account exists and can access all endpoints

## Milestone Summary

**Key Decisions:**

| Decision | Rationale | Phase |
|----------|-----------|-------|
| Default role is 'admin' not 'super_admin' | Security - super_admin must be explicitly assigned | 17-01 |
| Guard order: AdminAuthGuard then AdminRolesGuard | AuthGuard populates user.role needed by RolesGuard | 17-03 |
| Role stored directly in JWT payload | Avoids database lookup on every request for role check | 17-02 |
| AdminInvitation uses SHA256 token hashing | Security - store hashes not raw tokens to limit exposure | 19-01 |
| ADMIN_RBAC_ENABLED defaults to false | Requires explicit 'true' for safety during rollout | 23-01 |
| PagerDuty skips warning severity alerts | PagerDuty for critical/error only, warnings go to Slack (ALERT-07) | 21-04 |
| Dedup key format: nebuladns:{source}:{type}:{identifier} | Prevents incident explosion by grouping related alerts | 21-04 |

**Issues Resolved:**
- Secure credential storage for alert integrations using AES-256-GCM encryption
- Self-escalation prevention in role management
- Safe RBAC rollout with feature flags and shadow mode
